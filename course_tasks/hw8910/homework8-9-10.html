ДЗ 8+9+10. Починить выпуск модели и доказать, что сервис работает правильно

Инженерный кейс: расследование ошибок → исправления → собственные тесты → работающий сервис.

Ситуация. Команда обновила принятую модель, но API продолжает отвечать старой. Неполный отчёт иногда получает зелёный выпуск, повтор запуска размножает публикации, а после изменения данных используется старый результат подготовки. Вам передают исполняемый прототип с семью независимыми дефектами. Нужно восстановить причины и довести его до проверяемого процесса выпуска.

Результат работы — ваш исправленный проект. Одного запуска готовых команд и скриншота зелёных тестов недостаточно. Только исправление release.py и прохождение приложенных проверок дают максимум 2 из 10. Остальные баллы — за процесс, сервис, собственные эксперименты и доказательства.

Стартовый проект находится в папке hw8910-broken рядом с этим файлом.

Стартовый комплект

hw8910-broken/ содержит работающий, но некорректный прототип:

  • lab.py — подготовка с кешем, принятие версии и журнал публикаций.
  • service.py — локальный HTTP-сервис с лёгким StubBackend, прогревом и диагностикой вызовов.
  • release.py — ключ кеша, проверка отчёта и запись указателя; реализации содержат ошибки.
  • INCIDENTS.txt — сценарии расследования; CONTRACTS.txt — ожидаемые контракты.
  • 13 открытых тестов проверяют только часть требований. Недостающие проверки пишете вы.

Имитатор выдаёт явно помеченные ответы STUB ONLY. Он позволяет проверять управление процессами, HTTP и сбои без модели, сети и дополнительных пакетов. После исправления перенесите процесс в Prefect, HTTP-контракт — в FastAPI, а backend замените загрузчиком своей модели из ДЗ 6+7. Тесты управления должны работать с обоими вариантами через общий интерфейс backend.

python3 lab.py init
python3 lab.py run --fail-after-prepare  # намеренный сбой
python3 lab.py run                      # прототип сообщает PUBLISHED
python3 service.py --port 8091 --warmup-seconds 10
# В другом терминале исследуйте /health, /ready, /debug и /generate.
# Команды запуска — начало расследования, не выполненное задание.

Быстрые тесты работают на Python 3.12 без дополнительных пакетов и без модели. Зависимости реального потока и сервиса закрепите отдельно. При переносе в свой репозиторий сохраните существующие тесты ДЗ 6+7.

0. Расследование и свои доказательства

  1. Сохраните исходную версию прототипа отдельным коммитом. Для каждого из семи дефектов заполните defects.csv: симптом, команда воспроизведения, фактический/ожидаемый результат, причина, исправление и имя регрессионного теста. Несколько симптомов одной причины не считайте разными дефектами.
  2. Напишите не менее шести собственных интеграционных тестов сверх приложенных 13. Минимум три обращаются к реальному локальному HTTP-серверу; минимум два запускают процесс выпуска через subprocess с отдельным рабочим каталогом; ещё один проверяет повторную публикацию или откат. Модель в этих тестах заменяется stub, но HTTP, файловая система и границы процессов настоящие.
  3. Обязательное покрытие: отказ и несовместимый отчёт; сбой/восстановление; изменение входа; повтор выпуска; готовность; фактически загруженная версия; неверный запрос без вызова backend. Один тест может содержать несколько связанных этапов.
  4. Покажите, что каждый новый тест выявляет нужный дефект исходного прототипа и проходит на исправленном. Ошибка импорта, несуществующая команда или изменённое имя маршрута не считаются доказательством. При смене фреймворка сохраните совместимый интерфейс тестового запуска.
  5. Исправьте причины, затем перенесите стадии и HTTP в целевую архитектуру. Нельзя убрать отрицательные проверки, заменить ответы заранее заготовленными PASS или переписать тесты под сломанное поведение.

Отдельный опыт: после запуска сервиса на версии A опубликуйте B. Проверьте старую версию до загрузки, новую после перезапуска, затем выполните управляемый откат к ранее принятой A. Эти проверки выполняются на двух лёгких STUB-версиях. Реальное подключение модели проверяется отдельно.

A. Процесс выпуска и восстановление

подготовка входа → получение артефакта → проверка полного eval
                                          ├─ отказ → отчёт, прежняя версия
                                          └─ PASS → accepted.json → загрузка API
  1. Оформите один Prefect-flow с отдельными задачами подготовки, получения/проверки артефакта, оценки допуска и публикации. Передавайте небольшие описания: URI, run ID, версии и хеши. Веса и тензоры не передаются как результаты задач.
  2. В этой работе стадия получения артефакта может читать готовый training run из ДЗ 6+7. Подпишите это явно: чтение результата не означает повторное обучение.
  3. Кешируйте одну реальную стадию подготовки: например, проверку/токенизацию данных. Ключ учитывает содержимое входа, точную версию токенизатора, шаблон, длину и версию кода обработки. Сохраните результат так, чтобы он читался после завершения процесса.
  4. Внесите управляемый сбой после подготовки. Повторите flow в новом процессе без сбоя: подготовка должна использовать сохранённый результат. Затем измените содержимое входа по тому же пути — прежний кеш использовать нельзя. Покажите состояние задач/журнал, а не только одинаковый результат.
  5. Повтор одинакового успешного выпуска, включая повтор в другом процессе, не создаёт дубликаты в журнале публикаций и не меняет смысл принятого указателя. Разделите журнал попыток и события фактического выпуска. Идентификатор выпуска должен учитывать модель, runtime и связанное решение допуска. Для этой работы достаточно одного писателя. Добавьте опыт со сбоем между обновлением указателя и записью журнала: повтор должен восстановить согласованность без двойного события. Можно изменить формат хранения; выбор объясните. При сохранении файлового указателя требуется атомарная замена JSON. Отказ и ошибка записи оставляют прежний файл побайтно неизменным.

Временную сетевую ошибку можно повторять ограниченно. Неверную схему, несовместимые веса и отказ по качеству повтором не исправляют. Расписание и запуск за исторические периоды в обязательную часть не входят.

B. Допуск и быстрые проверки

  1. Сохраните правило качества из ДЗ 6+7: общая accuracy/format rate, критические срезы и behavioral-кейсы. Один val_loss не заменяет оценку поведения.
  2. Обвязка должна вызвать ваше правило допуска или проверить сохранённый результат с исходными отчётами и их хешами. Создайте связанный с ним release-report.json. Нельзя вручную вписать passed: true и считать это оценкой.
  3. Зафиксируйте manifest: model ID, URI артефакта, хеш файлов модели, точную ревизию базы, токенизатор, шаблон, параметры генерации, dtype и хеши протокола/golden set. Runtime должен совпадать у оценки и API; при изменении нужна новая оценка.
  4. Дополнительно проверьте контракт в validate_release: полный отчёт, настоящий boolean PASS, конечные метрики и совпадающие версии/хеши. Missing, NaN/Inf, чужой отчёт или несовместимый runtime закрывают выпуск. Перед выпуском и загрузкой пересчитайте хеши самих файлов.
  5. Пройдите приложенные тесты и включите свои интеграционные проверки из раздела 0 в один быстрый запуск без весов. Число и смысл вызовов stub проверяются тестами; для итоговой демонстрации нужен настоящий ответ вашей модели.
  6. Запустите быстрые проверки без загрузки весов. Покажите зелёный прогон и намеренную поломку с ненулевым кодом завершения; затем восстановите код. При доступных Actions можно выполнить те же команды там. Локальный вариант полностью засчитывается.

C. Сервис выбранной модели

  1. Поднимите локальный API с GET /health, GET /ready и POST /generate. Health подтверждает жизнь процесса; ready успешен только после загрузки нужных весов и прогрева. При фоновой загрузке до готовности верните 503. При блокирующем startup сервер до завершения загрузки может вообще не принимать соединения — это допустимо.
  2. Сервис читает принятый manifest, проверяет файлы и загружает указанную базу/адаптер с теми же условиями, что использованы при оценке. Не подменяйте случайным локальным конфигом. Ограничьте длину входа, число новых токенов и параллельные вычисления.
  3. Зафиксируйте лимит генерации из протокола оценки. Если API допускает менять его на запрос, определите и проверьте поддерживаемый диапазон; произвольное изменение настроек не наследует прежний допуск.
  4. Ответ содержит текст, request_id, фактически загруженный model_id, runtime_sha256, число выходных токенов и длительности. Некорректный запрос, например чрезмерный лимит, получает 4xx до генерации.
  5. Изменение accepted.json само по себе не меняет модель в памяти. Покажите, что до перезапуска API сообщает прежний ID, а после загрузки согласованного выпуска — новый. Если второй реально допущенной версии нет, достаточно доказать загрузку текущего manifest после перезапуска и описать сценарий смены; фикстуру не выдавайте за новую модель.

Если кандидат честно не прошёл gate, сохраните отказ и обслуживайте принятую baseline-версию. Это не снижает балл. Для baseline тоже укажите происхождение, конфигурацию и реальную загрузку. Не ослабляйте пороги ради зелёного статуса.

D. Небольшой замер и объяснение

  • После прогрева выполните один и тот же набор из 8 запросов при параллельности 1 и 2. На медленном CPU допустимо 4+4 с явной пометкой. Используйте одинаковый лимит ответа и запишите фактическое число токенов.
  • Сохраните каждую попытку: ID, режим, статус/ошибку, клиентскую задержку, длительность генерации и model_id. Ошибки и тайм-ауты не удаляются из журнала.
  • В таблице укажите n, число успехов/ошибок, длительность всего пакета, успешные запросы/с, среднюю и максимальную задержку успешных запросов отдельно от ошибок. Объясните разницу между ожиданием и вычислением. На такой выборке не делайте вывод об устойчивом p95.
  • При едином JSON-ответе измеряется полная задержка; TTFT и ITL не выдумываем. Коротко объясните prefill/decode, расход памяти KV-cache и почему последовательный Transformers-сервис не доказывает скорость SGLang/vLLM.
