ДЗ 1 · Слайд 2/7

Окружение и структура проекта

Почему uv, а не pip

Нам нужен lock-файл: точная фиксация всех транзитивных зависимостей. Без него «работает у меня» не воспроизводится ни у соседа, ни в CI на девятой неделе. uv делает это быстро; poetry тоже допустим, pip install без версий — нет.

Установка
curl -LsSf https://astral.sh/uv/install.sh | sh

uv init mlops-course && cd mlops-course
uv add "torch" "transformers" "accelerate" "pyyaml" "psutil"
uv sync            # создаёт .venv и uv.lock
uv run python -c "import torch; print(torch.__version__)"

Структура репозитория

hw1-broken/
├── src/
│   ├── config.py       # чтение params.yaml
│   ├── model.py        # загрузка модели, chat template, генерация
│   ├── generate.py     # точка входа: печатает ответ
│   └── bench.py        # замеры
├── tests/
│   └── check.sh        # самопроверка, 5 пунктов
├── docs/
│   └── hardware.md     # ← ваш отчёт по этой работе
├── params.yaml         # ← имя модели живёт ЗДЕСЬ и только здесь

├── Makefile            # install / generate / bench / check

Структура задана жёстко: на неё опираются проверки всех последующих домашних работ.

ДЗ 1 · Слайд 3/7

params.yaml: главное требование курса

Конфиг

params.yaml
model:
  name: "Qwen/Qwen3-0.6B"   # SmolLM2-135M-Instruct / Qwen3-1.7B — по вашему железу
  dtype: "bfloat16"
  device: "auto"            # auto | cpu | cuda | mps

generate:
  max_new_tokens: 200
  temperature: 0.0          # 0 — жадный поиск, детерминированно
  seed: 42
  enable_thinking: false    # Qwen3 по умолчанию рассуждает вслух в <think>

bench:
  warmup_runs: 1            # прогрев обязателен, иначе замер занижен
  measure_runs: 3
  prompt: "Объясни, что такое MLOps, в трёх предложениях."

Правило

Имя модели встречается в проекте ровно один раз — в этом файле. Ни в одном .py его быть не должно. Проверка подменит значение и убедится, что код не потребовал правок.

src/config.py
import yaml
from pathlib import Path

def load_params(path: str = "params.yaml") -> dict:
    return yaml.safe_load(Path(path).read_text(encoding="utf-8"))

Зачем это на первой же неделе

Configuration debt из лекции — параметры, размазанные по коду. Проще не допустить его сразу, чем вычищать на восьмой неделе, когда файлов станет тридцать.

ДЗ 1 · Слайд 4/7

Инференс и детерминированность

Как устроена загрузка модели

Логика вынесена в src/model.py и переиспользуется генерацией и замерами — дублировать её нельзя. Ниже суть того, что там происходит.

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from config import load_params

p = load_params()
torch.manual_seed(p["generate"]["seed"])

tok = AutoTokenizer.from_pretrained(p["model"]["name"])
model = AutoModelForCausalLM.from_pretrained(
    p["model"]["name"],
    dtype=getattr(torch, p["model"]["dtype"]),
    device_map=p["model"]["device"],
)

messages = [{"role": "user", "content": p["bench"]["prompt"]}]
text = tok.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=True,
    enable_thinking=p["generate"]["enable_thinking"],   # ← иначе Qwen3 выдаст <think>
)
inputs = tok(text, return_tensors="pt").to(model.device)

out = model.generate(
    **inputs,
    max_new_tokens=p["generate"]["max_new_tokens"],
    do_sample=p["generate"]["temperature"] > 0,   # TODO: обработать temperature=0
)
print(tok.decode(out[0][inputs.input_ids.shape[1]:],
                 skip_special_tokens=True))

На что обратить внимание

  • apply_chat_template — не собирайте промпт конкатенацией строк. К четвёртой лекции станет понятно, почему это критично; привыкайте сразу
  • Детерминированность — при temperature = 0 два прогона обязаны дать побайтово одинаковый вывод. Это проверяется
  • Обрезка промпта — generate возвращает вход вместе с ответом; срез [input_len:] обязателен
  • dtype на CPU — если bfloat16 на вашем процессоре медленнее float32, зафиксируйте это в отчёте: это осмысленный результат замера
  • Режим рассуждений Qwen3 — по умолчанию шаблон включает <think>-блок, и первые 200 токенов окажутся не ответом, а рассуждением. Передавайте enable_thinking из конфига. У других моделей этого параметра нет — шаблон его молча проигнорирует
ДЗ 1 · Слайд 5/7

Как честно померить машину

Три числа — три разных замера

МетрикаЧто измеряемТипичная ошибка
Время загрузкиот старта до готовности моделисмешать с генерацией
tokens/secтолько сама генерация, после прогревавключить загрузку — цифра занижена в разы
Пиковая RSSмаксимум за весь процессснять один раз в конце вместо максимума
src/bench.py — идея
t0 = time.perf_counter()
model = load_model()                 # ← время загрузки
load_time = time.perf_counter() - t0

for _ in range(p["bench"]["warmup_runs"]):
    generate(model)                  # ← прогрев НЕ засчитывается

times = []
for _ in range(p["bench"]["measure_runs"]):
    t = time.perf_counter()
    n_tokens = generate(model)
    times.append((time.perf_counter() - t, n_tokens))

# TODO: медиана tokens/sec, а не среднее — устойчивее к выбросу
# TODO: peak RSS через resource.getrusage или отдельный поток с psutil

Почему прогрев обязателен

Первый прогон включает выделение памяти, компиляцию ядер, прогрев кэшей. Без warmup вы измеряете не производительность машины, а стоимость первого запуска — и получаете число, заниженное в разы. Тот же принцип вернётся в ДЗ 10 при замере TTFT.

ДЗ 1 · Слайд 6/7

Что сломано в hw1-broken

Четыре заложенных дефекта

Ищите их сами — ниже описаны симптомы, а не строки.

  • Имя модели захардкожено в трёх местах — вместо чтения из params.yaml. Симптом: меняете конфиг, ничего не происходит. Прямое нарушение главного правила курса
  • Зависимости без версий — в requirements просто torch, transformers. Симптом: у соседа другая версия и другое поведение; в CI на девятой неделе сборка сломается сама собой
  • bench.py меряет время вместе с загрузкой модели — и выдаёт бессмысленные tokens/sec. Симптом: цифра неправдоподобно мала и почти не зависит от длины ответа
  • Генерация не воспроизводится — в конфиге включён сэмплинг, а seed не зафиксирован. Симптом: два запуска подряд дают разный текст, хотя задание требует детерминированности

Требование к отчёту

В docs/hardware.md отдельным разделом опишите каждый найденный дефект: в чём он был, как проявлялся и как исправлен. Простое «починил» не засчитывается.

Что делает tests/check.sh

1. Имя модели не захардкожено в коде
