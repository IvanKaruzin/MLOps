A. Учёт и выбор кандидата

  1. Исправьте четыре дефекта: общий run для разных моделей, потерю файлов после замены контейнера, отсутствие версий train/val и обход порога по loss.
  2. Получите минимум шесть отдельных законченных runs. Фиксируйте базу, данные, seed и бюджет; меняйте lr, r и target_modules.
  3. Бюджет по умолчанию: 4 шага на конфигурацию, train-пул 32, val 8, batch 1 × accumulation 2. Test не участвует в выборе. Увеличивать бюджет нужно одинаково для всех кандидатов.
  4. Сравните loss и ресурсы. После loss-порога зарегистрируйте версию с alias candidate. Это ещё не допуск в champion.
  5. Докажите сохранность probe-файла после пересоздания контейнера и загрузку candidate в новом процессе без локального конфига.

B. Проверка качества ответов

  1. Соберите минимум 50 собственных проверенных golden-примеров вне train и минимум три осмысленных среза. Набор хранится в DVC; сохраните источник и разметку. Экспортируйте полный индекс исходных train-вопросов для проверки утечки.
  2. Заранее закрепите протокол и критические срезы. Один prompt, один лимит генерации и один scorer применяются к обеим версиям. Впервые baseline — база с закреплённой ревизией, затем явно принятая версия.
  3. Реализуйте scorer: строгий JSON с полем answer, общая accuracy, format rate и срезы с n/counts. Пустые, неправильные и аварийные ответы остаются в знаменателе.
  4. Полностью оцените только baseline и одного кандидата, а не все шесть моделей. Сохраните сырые ответы, per-item результаты и списки исправленных/потерянных ответов в MLflow.
  5. Добавьте минимум три behavioral-кейса: формат, перефраз и корректный отказ по правилам своей задачи.
  6. Реализуйте gate: общая accuracy и format rate не ниже baseline, критические срезы не хуже, все обязательные behavioral-кейсы проходят. Missing/NaN/ошибка/несовместимость дают отказ. Порог не ослабляется после просмотра результата.
  7. Докажите отказ на испорченной копии ответов. Только после PASS выполняется make promote и назначается champion. Отказ по качеству — допустимый итог; candidate остаётся доступным.

LLM-as-judge и платный API не обязательны. Разберите 3–5 пар ответов вручную и кратко объясните ограничения метрик сходства и модельного судьи. Автоматический поиск перефразов не гарантирует отсутствия всех утечек.

Один порядок работы

uv sync --frozen
make check-eval          # после реализации двух функций; без модели
make up
make sweep
make report
make candidate          # loss-порог → alias candidate
make baseline-init      # один раз, без перезаписи baseline
make evaluate           # реальные ответы двух версий
make eval               # правило допуска по готовым ответам
make check-negative     # ожидаемый отказ на испорченной копии
make promote            # только при PASS → champion
make check-storage
make check-all          # 9 проверок MLflow + тесты оценки

Если качество не прошло — пропустите promote, сохраните отказ и состояние champion. Проверки хранения и загрузки используют candidate, поэтому отказ не мешает сдать работу. Отдельная команда make baseline-update обновляет baseline только после принятия, сохраняя историю.

Если ДЗ 6 уже выполнено

Используйте готовые runs, модель и исправления. Добавьте каталог evaluation, новые тесты и команды из архива. Не меняйте src, train/val и params.yaml без необходимости: это сохраняет связь с выполненным sweep. Изменения только кода оценки не требуют повторного обучения. Детали переноса — в README.
