Лекция 2 · Слайд 2/15

Вес, функция, выход

Прежде чем разбирать блок, договоримся о трёх словах. Без них дальше будет каша.

Вход

Токен внутри модели — это не буквы. Это столбик из 1024 чисел. Всё, что модель на данный момент про этот токен «думает», лежит в них.

Вес

Рядом лежит таблица чисел — матрица. Её никто не писал руками, она получилась при обучении. Это и есть веса. Файл модели — это буквально они и ничего больше: у Qwen3-0.6B таких чисел 596 миллионов.

Применить функцию

Это умножение. Берём одну строку таблицы, поэлементно перемножаем со столбиком, складываем — получилось одно число выхода. Повторяем для каждой строки.

Выход

Строк в таблице 1024, значит на выходе снова 1024 числа — ровно того же размера, что и вход. Именно поэтому такие блоки можно ставить друг за другом, и Qwen3 ставит их 28 раз подряд.

Обучение — это подкрутить числа в таблице, больше ничего. В ДЗ 2 вы будете крутить не всю таблицу, а маленькую добавку к ней — это и есть LoRA.

Лекция 2 · Слайд 3/15

Читаем строчку x = x + f(x)

Разберём эту строчку заранее, чтобы на следующем слайде она не выглядела заклинанием.

Главное: блок не выдаёт «нового токена». Он выдаёт поправку — столбик того же размера, — и её прибавляют к тому, что было.

Посмотрите на строчку внимательно: x стоит в ней два раза. Один раз внутри скобок — это аргумент функции. Второй раз снаружи — это слагаемое. Функция получает x на вход, но её результат не заменяет x, а складывается с ним. То, что x попадает в ответ напрямую, минуя функцию, и называется residual.

На числах

x     = [0.50, -1.20,  0.30, 2.10]
Δ     = [0.10,  0.05, -0.40, 0.20]
x + Δ = [0.60, -1.15, -0.10, 2.30]

Новый вектор — это почти старый. Было 2.10, стало 2.30, а не 0.20. Блок подвинул состояние, а не переписал его.

Что будет без плюса

Уберите residual — и новым x станет сама Δ: [0.10, 0.05, -0.40, 0.20]. От исходных чисел не осталось ничего. Повторите 28 раз — модель забудет, каким токен был на входе.

Каждый слой дописывает свою правку на полях, а не переписывает страницу заново.

Residual — прибавляем, а не заменяем. Это уже разобрали.

Осталось разобраться с norm. Это функция, которая приводит столбик чисел к одному масштабу — про неё весь следующий слайд. Здесь важно только где она стоит: внутри скобок или снаружи.

Где стоит норма

pre-norm Норма внутри скобок: x + f(norm(x)). Нормализуют только аргумент функции. Само x попадает в сумму как есть — его не трогают ни на одном из 28 слоёв. Qwen3, Llama, GPT-2 и дальше
post-norm Норма снаружи: norm(x + f(x)). Нормализуют уже сумму, то есть и x тоже. За 28 слоёв x пересчитывается 28 раз — и обучение от этого капризничает. трансформер 2017, BERT 
# post-norm — трансформер 2017
def block(x):
    x = norm(x + Attention(x))
    x = norm(x + MLP(x))
    return x

# pre-norm — Qwen3 и всё современное
def block(x):
    x = x + Attention(norm(x))
    x = x + MLP(norm(x))
    return x
прогрев · warmup Первые несколько сотен шагов обучения learning rate держат почти нулевым и плавно поднимают до рабочего. Если дать полный шаг сразу, веса на первых же батчах улетают и обучение разваливается. Post-norm без прогрева просто не сходится — поэтому от него и ушли.
Лекция 2 · Слайд 5/15

Что такое нормализация

Сразу оговорка: «норма» здесь — не длина вектора, как в математике. Это название слоя, который нормализует.

Зачем она

За 28 слоёв числа в столбике разъезжаются: одни каналы вырастают до сотен, другие падают почти в ноль. Обучение от этого разваливается.

Нормализация приводит столбик к одному масштабу. Делит все 1024 числа на одно общее число так, чтобы их типичная величина стала около единицы. Пропорции между каналами сохраняются, меняется только общий размер — как перевести суммы в одну валюту, прежде чем складывать.

RMSNorm Считает корень из среднего квадрата и делит на него. Всё. Плюс один вектор обучаемых множителей. 2 действия · 1024 параметра на норму
LayerNorm Сначала вычитает среднее, потом делит на среднеквадратичное отклонение, потом ещё прибавляет обучаемый сдвиг. 4 действия · 2048 параметров на норму

Качество то же, а операций и параметров вдвое меньше — поэтому все перешли на RMSNorm.

# g — 1024 обучаемых множителя, по одному на канал
def rmsnorm(x, g):
    rms = sqrt(mean(x ** 2))
    return x / rms * g

# на нашем столбике из четырёх чисел
x          = [0.50, -1.20, 0.30, 2.10]
mean(x**2) = 1.5475  →  rms = 1.244
x / rms    = [0.40, -0.97, 0.24, 1.69]

# большое осталось большим, знаки на месте,
# но всё съехало к единице по величине

Лекция 2 · Слайд 6/15

Q, K, V — чем ищем, по чему ищем, что забираем

Attention отвечает на один вопрос: для каждого токена — на какие из предыдущих смотреть и что у них забрать. Чтобы это посчитать, из одного и того же x тремя разными таблицами весов делают три разных столбика.

Q — query, запрос«что я ищу». Считается из q_proj.
K — key, ключ«по чему меня можно найти». Из k_proj.
V — value, значение«что у меня можно забрать». Из v_proj.
голова, headодин комплект (q, k, v) на 128 чисел вместо 1024. Голов много, и каждая смотрит на своё.

Аналогия — картотека

Q — запрос, написанный на бумажке. K — надписи на корешках папок. V — то, что лежит внутри папки. Запрос сравнивают с каждым корешком, а достают содержимое. Поэтому K и V — разные вещи: по одному ищут, другое забирают.

Q, K и V — это не части модели, а три столбика чисел, посчитанные из x на каждом слое заново.

# из одного x — три столбика
q = x @ W_q      # что я ищу
k = x @ W_k      # по чему меня искать
v = x @ W_v      # что у меня забрать

# насколько токен j подходит токену i
score[i][j] = dot(q[i], k[j]) / sqrt(128)

w      = softmax(score[i])       # в сумме 1
out[i] = sum(w[j] * v[j] for j)  # что забрали
# «кот сел на ковёр», считаем для слова «ковёр»
             кот    сел     на   ковёр
score  = [  2.100, 0.400, 3.000, 1.200]
softmax= [  0.247, 0.045, 0.607, 0.100]

out = 0.247·v(кот) + 0.045·v(сел)
    + 0.607·v(на)  + 0.100·v(ковёр)
Лекция 2 · Слайд 7/15

Attention и GQA

Четыре таблицы весов в каждом блоке

Три из них мы уже знаем: q_proj делает запрос, k_proj — ключ, v_proj — значение. Четвёртая, o_proj, склеивает результаты всех голов обратно в один столбик на 1024 числа.

GQA — Grouped Query Attention, «внимание со сгруппированными запросами»

Идея: голов запроса пусть будет много, а наборов ключей и значений — вдвое меньше, и пусть каждая пара Q-голов пользуется общим набором K и V. У Qwen3-0.6B это 16 голов запроса на 8 KV-голов. Зачем — станет ясно на следующем слайде: кэшируются именно K и V. А пока это видно прямо в размерах весов.

  • 16 голов × 128 (head_dim) = 2048 — отсюда первая размерность q_proj
  • Экономия не столько в параметрах, сколько в KV-cache: он тоже вдвое меньше. Об этом следующий слайд
Лекция 2 · Слайд 8/15

KV-cache: почему второй токен дешевле первого

Две фазы генерации

  • Prefill — весь промпт прогоняется за один проход, параллельно. Упирается в вычисления
  • Decode — токены рождаются по одному. Каждый новый токен смотрит на все предыдущие, но пересчитывать их k и v не нужно: они уже посчитаны и лежат в кэше. Упирается в память

Поэтому первый токен ждёшь дольше остальных — это TTFT, к ней вернёмся на лекции про сервинг.

Что именно лежит в кэше

Для каждого уже обработанного токена хранятся его k и v — по одной паре на каждую из 8 KV-голов, и так на каждом из 28 слоёв. q не кэшируется: запрос нужен только тому токену, который генерируется прямо сейчас; прошлым он больше не понадобится. Сам столбик x тоже не хранится — из него всё уже посчитано.

Чем платим

       2  — k и v, две штуки на токен
×     28  — на каждом слое свои
×      8  — по паре на KV-голову (не 16 — это GQA)
×    128  — длина одного вектора k или v
×   1000  — сколько токенов уже обработано
×      2  — байта на число в bf16
  ─────────
  ≈ 115 МБ  на один запрос длиной 1000 токенов
Лекция 2 · Слайд 9/15

Сколько запросов держит сервис

Следствия, которые вылезут позже

  • Кэш растёт линейно с длиной и на длинном контексте догоняет веса модели
  • Без GQA в формуле стояло бы 16 вместо 8 — кэш вдвое больше. Вот где настоящая экономия
  • Кэш живёт на каждый запрос: веса одни на всех, кэш — свой у каждого. Именно он ограничивает, сколько запросов сервис держит разом

Отсюда растут два приёма

PagedAttention · vLLM Кэш хранится страницами, как виртуальная память в операционной системе. Не нужно резервировать место под максимально возможную длину ответа — память не простаивает, запросов влезает больше.
RadixAttention · SGLang Одинаковое начало у разных запросов хранится один раз. Один системный промпт на тысячу запросов — одна копия кэша вместо тысячи.

Оба приёма разберём на лекции про сервинг. Пока важно понять, что оптимизируют именно кэш, а не веса.

Лекция 2 · Слайд 10/15

RoPE: откуда модель знает порядок слов

RoPE — Rotary Position Embedding, «вращательное кодирование позиции».

Зачем вообще

Формула внимания с прошлого слайда — dot(q[i], k[j]) — не содержит номеров токенов. Перемешайте слова, и все скалярные произведения останутся теми же: «собака укусила человека» и «человек укусил собаку» для такой модели одно и то же.

Идея

  • Позицию не прибавляют к вектору. Координаты берут парами и поворачивают пару на угол, пропорциональный номеру позиции: токен на позиции m — на угол m · θ
  • Поворот делают только у q и k — у того, чем ищем, и у того, по чему ищем. v не трогают: содержимое папки от её места на полке не меняется
  • Обучаемых параметров RoPE не добавляет: углы считаются по формуле

Главное свойство

Скалярное произведение повёрнутых векторов зависит только от разности позиций: модель видит «на сколько токенов раньше», а не абсолютный номер. Справа это можно проверить на калькуляторе.

Для ДЗ важно одно: RoPE не добавляет обучаемых параметров, и в таблице параметров вы его не найдёте.

# берём одну пару координат вектора
# и поворачиваем её на угол m * theta
def rope(pair, m, theta):
    x1, x2 = pair
    a = m * theta
    return (x1*cos(a) - x2*sin(a),
            x1*sin(a) + x2*cos(a))
# theta = 0.5, пара (1.0, 0.0)
позиция 3 → (  0.0707, 0.9975 )
позиция 5 → ( -0.8011, 0.5985 )

# их скалярное произведение
0.0707·(-0.8011) + 0.9975·0.5985 = 0.5403

# а теперь просто косинус разности позиций
cos( (5 - 3) · 0.5 ) = cos(1.0)   = 0.5403

# то же число. Абсолютные позиции сократились
практическое следствие Длина контекста упирается в углы, на которых модель обучалась. У Qwen3-0.6B max_position_embeddings = 40 960. Дальше — экстраполяция и падение качества; отсюда приёмы вроде масштабирования базы RoPE уже после обучения.
Лекция 2 · Слайд 11/15

MLP: где лежит половина модели

MLP — multi-layer perceptron, «многослойный перцептрон». Обычная маленькая нейросеть: умножили на таблицу, применили нелинейность, умножили на другую.

Зачем она нужна

Здесь лежит то, что модель знает. Столбик разворачивают в 3072 числа — это широкое пространство работает как память, ячейки реагируют на свои сочетания признаков, а down_proj складывает сработавшие обратно в 1024. Attention притащил информацию от соседей — MLP решает, что она значит.

Чем отличается от внимания

attention — смешивает токены Токен смотрит на другие токены и забирает у них. Работает поперёк последовательности. Отвечает на вопрос «откуда взять».
MLP — ничего не смешивает Каждый токен прогоняется отдельно и соседей не видит вообще. Работает вглубь одного столбика. Отвечает на вопрос «что с этим делать».
а рассуждение? а reasoning? Отдельного «модуля рассуждений» в архитектуре нет. Блок <think> у Qwen3 — это не слой, а поведение: модель просто пишет больше промежуточных токенов, и на каждом работают всё те же 28 блоков. В ДЗ 2 вы это увидите: строки про reasoning в таблице параметров не будет. 
# SwiGLU: три таблицы вместо двух
MLP(x) = down_proj( SiLU(gate_proj(x)) * up_proj(x) )

gate_proj решает, что пропустить, up_proj считает, что именно, поэлементное умножение работает вентилем, down_proj возвращает в 1024.

# параметров на один слой
attention  q 2048×1024 + k 1024×1024
         + v 1024×1024 + o 1024×2048
                                = 6 291 456

MLP        gate 3072×1024 + up 3072×1024
         + down 1024×3072
                                = 9 437 184

9 437 184 / 6 291 456           = ровно 1,5

Лекция 2 · Слайд 14/15

Ловушка: RSS покажет вам не то

RSS · Resident Set Size «Резидентный размер» — сколько памяти процесса физически лежит в оперативке прямо сейчас. Не выделено, не зарезервировано, не в свопе, а именно занято. Это то самое число, которое показывают top, диспетчер задач и «Мониторинг системы» в колонке «Память». ru_maxrss возвращает его пик за всё время работы процесса.

Тот же прогон, те же три режима. Только память снята не через аллокатор, а через ru_maxrss — ту самую метрику, которую советует половина туториалов.

РежимПик по аллокаторуПик RSS
инференс2222 МБ1920 МБ

Разброс RSS по трём режимам — 128 МБ. При том что полное дообучение добавляет 3411 МБ настоящей памяти. Метрика не отличила полное дообучение от инференса вообще.

почему так На Apple Silicon тензоры живут в буферах Metal. Это память устройства, и в резидентную память процесса она попадает лишь частично. RSS честно меряет то, что умеет мерить, — просто это не то, что вам нужно.
что мерить вместо неё torch.mps.driver_allocated_memory() на Apple Silicon, torch.cuda.max_memory_allocated() на NVIDIA. На чистом CPU RSS как раз работает — там тензоры и правда лежат в памяти процесса.

Простая проверка на вменяемость: веса модели в bf16 занимают 1137 МБ. Меньше этого числа пик быть не может ни в одном режиме. Если у вас меньше — вы измерили не то.

Во второй волне работ у одного RSS вышла 578 МБ, у другого 1001,8. Оба числа меньше весов модели, и никто не остановился и не перепроверил.
