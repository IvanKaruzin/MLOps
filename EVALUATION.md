# Часть B. Оценка ответов и допуск в champion

## Свои данные

Создайте три файла, ориентируясь на `examples/*.example.jsonl`:

- `data/eval/golden.jsonl`: минимум 50 вручную проверенных вопросов своей
  темы вне train. Поля: `id`, `group_id`, `input`, `expected` (строковая
  метка), `choices` (допустимые метки), `slices` и `source`.
- `data/eval/training-index.jsonl`: **полный список исходных вопросов train**
  с `id`, `input`, `group_id`, полученный из тех же сырых данных, что в ДЗ 4.
  Не заменяйте его одной строкой из примера. Покажите связь с токенизированным
  train через DVC/исходный пайплайн; тензоры нельзя достоверно проверить
  простым сравнением текстовых строк.
- `data/eval/behavioral.jsonl`: минимум три кейса того же формата с `type`:
  `format`, `paraphrase`, `refusal`. Для отказа заранее задайте границу темы
  в system-инструкции и ожидаемую метку, например `REFUSE`. Для перефраза
  свяжите пару через `group_id`; при смене порядка вариантов обновите метку.

Не копируйте один вопрос 50 раз с новыми id. Вручную проверьте неоднозначность,
эталон и источник. Группы одного вопроса/документа разделяются до train/eval.
Автопроверка ловит точное нормализованное совпадение и пересечение group_id,
но **не доказывает отсутствие всех смысловых перефразов**. Ручной разбор нужен.
Behavioral-кейсы могут быть связаны с golden; они считаются отдельно,
не увеличивают его n и не выдаются за независимую статистику.

Подключите файлы проверки к DVC в своём репозитории ДЗ 4-5; в Git сохраните
`.dvc`, конфиг, код подготовки и инструкции доступа. Сам набор должен быть
доступен преподавателю. `expected` не включается в prompt: модель видит
только `input` и общую system-инструкцию.

## Один протокол

Настройте `evaluation/params.json`: пути, свою system-инструкцию, лимит
ответа и хотя бы один критический срез. Всего в golden должно быть ≥3
осмысленных среза; они могут пересекаться. До оценки запишите в выводе,
почему эти группы важны. Не суммируйте пересекающиеся группы в общий n.

Обвязка использует одну system-инструкцию, `do_sample=False`, один seed,
один лимит токенов и один scorer для обеих моделей. Prompt оценки может
отличаться от prompt обучения, но одинаков для baseline и кандидата.
Все части протокола и код оценки входят в его SHA256. Точные ревизии
моделей закреплены отдельно. Повторное использование golden помогает
разработке; итог не следует называть независимым аудитом качества.

## Функция score

На входе список заданий и список фактических ответов по id. Ответ валиден
только как JSON с **единственным** полем `answer`, строкой из `choices`.
Верный ответ требует валидности и совпадения с `expected`.

Пример на трёх вопросах: верный JSON, неверный JSON, timeout.
Общая accuracy равна 1/3, а не 1/2. Формат оценивается отдельно.
Timeout и другие ошибки генерации остаются в знаменателе и в поле `error`.
Ни одна строка не исчезает из `per_item`.

Верните:

```text
overall: n, correct, valid, errors, accuracy, format_rate
slices: {имя_группы: те_же_поля}
per_item: [{id, raw, parsed, valid, correct, error, slices}, ...]
```

Несовпадающие id, дубли и пустой набор - ошибка контракта. Плохой ответ
модели - строка с нулевым результатом. Эти ситуации различаются.

## Функция quality_gate

На входе два отчёта и список критических срезов. До допуска проверьте:

1. Совпадают `protocol_sha256`, `golden_sha256`, `baseline_spec_sha256`.
   Оба отчёта полные и содержат конкретную модель.
2. Набор непустой, golden содержит ≥50 строк, ≥3 среза; одинаковые id,
   имена срезов и размеры групп. Метрики конечны и соответствуют counts.
3. В generation нет ошибок. Общая accuracy и format_rate кандидата
   не ниже baseline. В каждом критическом срезе accuracy не ниже baseline.
4. Все обязательные behavioral-кейсы кандидата прошли, их минимум три.

PASS возвращает словарь с `passed=True`. Любая несовместимость, missing,
NaN, ошибка или регрессия вызывает `ValueError`. Допуск ухудшения равен нулю.
Обвязка перед продвижением заново считает метрики из сохранённых raw-ответов
и сверяет хеши. Условия нельзя ослабить задним числом ради PASS.

`make check-eval` использует синтетические фикстуры, **не измерения Qwen**.
`make evaluate` получает реальные ответы и логирует их в MLflow.
`make eval` проверяет готовые отчёты без повторной генерации.
`make check-negative` портит **копию ответов**, а не веса: эта проверка
доказывает отказ gate, не качество самой генерации. Веса и alias не меняются.

## Результат

В `docs/conclusion.md` объедините части A и B:

- Какой run выбран по loss, бюджет и ограничения короткого поиска.
- Baseline и candidate: точные версии, общие accuracy/format_rate,
  ≥3 среза с n и исходными counts; какие id исправили и какие потеряли.
- Три behavioral-кейса, результат гейта и подтверждение отрицательного теста.
- 3-5 разобранных пар ответов; почему сходство слов не заменяет проверку
  правильности. Где был бы полезен judge и какие у него возможны искажения.
- Решение: приняли / не приняли. При отказе - причина и следующий шаг,
  без подмены baseline. При принятии - URI champion и связанный eval run.

LLM-as-judge, BLEU/ROUGE/BERTScore и платный API для обязательной части не
нужны. Если добавляете judge, скрывайте имена моделей, меняйте A/B и B/A,
восстанавливайте соответствие букв версиям, сохраняйте рубрику и вердикты
и сверяйте спорные случаи с человеком. Judge не заменяет scorer меток.
